# סליקה, הרשמה ואוטומציות — מצב בפועל

עודכן: 12.10.2026. בוצעה עבודת פיתוח ובדיקות מקומיות בלבד. אין חיבור לחשבון הסוחר, חיובים אמיתיים, שליחת הודעות, קבלות או שינוי נתוני ייצור.

## עדכון בעקבות בקשת חיבור Morning וקישורי סליקה

הבעלים אישר איתור credentials ב־Keychain ויצירת קישורי סליקה לפי הצורך. בדיקת הסביבה מצאה Linux, ללא `/usr/bin/security`, ללא secrets או outbound identities מוגדרים; אין כלי מחובר לגישה ל־Keychain של ה־Mac. חשבון Vercel המחובר כולל שלושה פרויקטים, ללא פרויקט תואם לאתר/ריפו הנוכחי. לא נקראו ערכי סודות מפרויקטים אחרים. מדיניות הרשת של סביבת הפיתוח מאפשרת כעת package-manager hosts בלבד, ולא את שרתי Morning.

`server/morning-credentials.mjs` וסקריפט `scripts/academy-keychain.mjs` מאפשרים הרצה **על ה־Mac של הבעלים**: קריאה ממוקדת של פריט JSON המכיל `id`/`secret` או `client_id`/`client_secret`, או שני פריטים נפרדים. אין dump של ה־Keychain, אין סריקה של פריטים שאינם Morning, ואין הדפסת מפתחות. האפשרות `--serve` מעבירה אותם בזיכרון לתהליך השרת בלבד; היא אינה מפעילה את ספק הסליקה.

```bash
npm run academy:keychain -- --check --service '<שם השירות של הפריט הקיים>'
# אם המזהה והסוד שמורים בנפרד:
npm run academy:keychain -- --check --id-service '<שם פריט המזהה>' --secret-service '<שם פריט הסוד>'
```

אין למסור את ערכי המפתחות בצ׳אט, בארגומנטים או במשתני `VITE_*`. בתשתית ענן יש לקשור `MORNING_API_ID` ו־`MORNING_API_SECRET` כסודות שרת, ולאפשר את שרתי ה־API הרשמיים אחרי אימות הכתובות.

נוספה `HostedCheckout` ב־`server/hosted-checkout.mjs`: יצירת קישור אחת לכל הזמנה באמצעות claim הנשמר ב־SQLite, ללא טרנזקציה פתוחה במהלך קריאה לספק. כשל/timeout עמום אינו יוצר קישור חדש בניסיון חוזר; המקום נשאר שמור עד התפוגה ונפתחת משימת בדיקה. קישור מוחזר לדפדפן רק אם יעד ה־HTTPS מופיע ברשימת origins של adapter שנבדק, ואם תוקפו אצל הספק אינו ארוך משמירת המקום. קופון המוריד מחיר לאפס חסום בזרימת הסליקה הזו ודורש מסלול הרשמה ללא גבייה שטרם מומש.

הדפדפן שומר token הזמנה בטאב ומעביר לדף הסליקה שקיבל מהשרת. בחזרה הוא בודק את מצב התשלום; polling מוגבל וניסיון חוזר ידני תומכים באישור שמתעכב. `POST /orders/:id/reconcile` דורש Bearer של ההזמנה. הנתיב `/payments/morning/notify/:id` הוא **אות לבדיקת ספק בלבד**: אף שדה callback אינו מקור אמת. רק תשובה שה־adapter קיבל בקריאת ספק מאומתת, עם מזהה קישור/הזמנה, סכום, מטבע ואסמכתא תואמים, יכולה להיכנס למנגנון הרישום. חוזה callback וה־acknowledgement הרשמי עדיין צריכים מימוש לפי מפרט Morning.

מצב `morning` קיים בליבה, אך adapter ברירת המחדל נשאר `ready=false`; הגדרת מפתחות לבדה אינה משנה זאת. token ההזמנה נגזר מ־`ACADEMY_ORDER_SECRET` נפרד, חזק וקבוע. אפשרויות הסימולציה והחזרי הדגמה חסומות במצב זה. בדיקות הספק המדומה מוכיחות מעבר, חזרה, אימות ורישום יחיד; **אינן בדיקת sandbox של Morning**.

קריאה נוספת ב־[תיעוד Morning הרשמי](https://developers.morning.co/) ובקישור `/api` מצאה explorer המבוסס JavaScript שלא חשף דרך כלי הקריאה את סכמות יצירת הקישור, lookup, callback ומסמכים. אין שימוש ב־endpoints משוערים ממקורות קהילה. להשלמה נדרשת הרצה עם גישה ל־Mac/סודות שרת ולמפרט הרשמי, ואז בדיקת חשבון וסביבת sandbox. קבלות, דיוור, CRM ואחסון ייצור נשארים חסמים כמפורט בהמשך.

## מה עובד בפיתוח

`server/commerce.mjs` משתמש ב־SQLite מובנה של Node 24, עם WAL, foreign keys, busy timeout ו־`BEGIN IMMEDIATE`. נתוני מועדים, קופונים, הזמנות, אירועי תשלום, הרשמות, outbox ויומן מנהל נשמרים בדיסק. ברירת המחדל היא סליקה חסומה. טיוטות אינן מוצגות כזמינות לרכישה. רק מועד עתידי, מאושר, מפורסם ופתוח להרשמה יכול לקבל הזמנה.

הקיבולת המרבית היא 12; מינימום להפעלה 8 **הרשמות ששולמו ואומתו**. הזמנה ממתינה שומרת מקום עד 15 דקות, לכל המאוחר עד תחילת הסמינר. מושבים שמורים נכללים בחישוב הזמינות אך אינם נספרים במינימום. כל שינוי מלאי והזמנה מתבצע בטרנזקציה. שמירה שפגה משחררת מקום; הצלחת תשלום שמגיעה מאוחר אינה תופסת את המקום מחדש אלא מסומנת `refund_required`, עם משימת בדיקה למנהל.

קופונים פרטיים נבדקים בשרת. תמיכה באחוזים או סכום באגורות, התאמה לסמינרים/מועדים, תוקף, מגבלה כוללת ומגבלה לאימייל. גם הזמנות ממתינות שומרות מכסת קופון; הזמנה שנכשלה או פגה משחררת אותה. החזר אינו מחדש אוטומטית מכסת קופון שמומשה. קופון נבדק שוב בעת אימות תשלום; שינוי בהנחה, ביטול קופון או סגירת מועד מונעים הרשמה ומחייבים בדיקה/החזר. מגבלת לקוח לפי אימייל אינה זיהוי אדם משפטי; זיהוי לקוח מאומת הוא חסם לייצור אם נדרשת מגבלה שאינה ניתנת לעקיפה באמצעות אימייל נוסף.

`Idempotency-Key` מונע הזמנות כפולות. בקשה חוזרת עם אותו מפתח ופרטים שונים נדחית. כל הזמנה מקבלת token הרשאה נפרד. השרת אינו חושף רשימת לקוחות, קופונים פרטיים או הזמנות דרך הקטלוג הציבורי.

בסימולציה מפורשת בלבד, השרת יוצר אירוע תשלום חתום ב־HMAC SHA-256 עם timestamp, בודק חתימה וחלון של חמש דקות, סכום, מטבע, אסמכתא, מצב הזמנה ותוקף המושב. מזהה אירוע ואסמכתת עסקה ייחודיים מונעים טיפול כפול. **פתיחת עמוד תודה או redirect בדפדפן אינם אישור תשלום.** סימולציה זו אינה סביבת בדיקות רשמית של Morning/Grow.

אישור תשלום יוצר הרשמה ועוד משימות נפרדות לאישור, הכנה, תזכורת, המשך ו־CRM. עם ההרשמה השמינית מתווספת התראת מינימום למנהל פעם אחת. קיימת נקודת בדיקה פנימית מוצעת 48 שעות לפני המועד: אם לא הושג מינימום, הדוח מסמן שנדרשת החלטת מנהל; אין ביטול אוטומטי ואין כאן מדיניות משפטית שאושרה.

החזר מנהל בפיתוח הוא **רישום סימולציה בלבד**. הוא משנה סטטוס, מבטל הרשמה ומשחרר מקום, מבטל הודעות שטרם נשלחו ומוסיף הודעת ביטול. הוא אינו מחזיר כסף אצל ספק אמיתי ואינו מפיק מסמך כספי.

## מחיר ומיסוי

המקור המשותף לשרת ולאתר הוא `shared/commerce-config.json`:

- השקה: 119,000 אגורות = 1,190 ₪.
- מחיר רגיל מתוכנן: 149,000 אגורות = 1,490 ₪; אין טענה שזה מחיר עבר.
- מטבע ILS, מחיר סופי, עוסק פטור, חישוב מס `none`, שיעור 0, מסמך מיועד `receipt`.
- שעות 15:00–20:00, משך חמש שעות, אזור זמן `Asia/Jerusalem`.

הגדרת מס מרכזית ואינה מוסיפה מע״מ. השרת מאמת את כללי 8/12, חמש שעות, ILS והמס הנוכחי בעת טעינה ונכשל במפורש אם מנסים לשנות אותם ללא מימוש מאושר. שינוי מחיר כרגע נעשה בקובץ זה, דורש הפעלה מחדש של השרת ובנייה מחדש של האתר. ממשק ניהול המחירים וגרסאות מחיר לייצור עדיין חסרים. שינוי מעמד מס מחייב אימות רו״ח וחשבון העסק וכן מימוש חישוב מס מאושר; אין להסתפק בשינוי מחרוזת `status`. לא מופקות קבלות מתוך שרת ההדגמה.

## הרצה בטוחה

דרישה: Node 24 ומעלה עם `node:sqlite`. אין תוספת תלויות npm.

```bash
# בתוך תיקיית הפרויקט. בחרו סודות חזקים שונים ושמרו אותם מקומית בלבד.
export NODE_ENV=development
export ACADEMY_ADMIN_TOKEN='<סוד-מנהל-אקראי-של-לפחות-32-תווים>'
export ACADEMY_SIMULATION_SECRET='<סוד-סימולציה-אקראי-של-לפחות-32-תווים>'
export ACADEMY_PAYMENT_MODE=disabled
node scripts/academy-server.mjs
```

השרת מאזין כברירת מחדל ב־`127.0.0.1:5174`; Vite מפנה אליו `/api/academy`. SQLite נשמר ב־`.local/academy.sqlite`. אין להוסיף את `.local/` ל־git, לפרסם אותו או למחוק אותו אם יש נתוני בדיקה שחשוב לשמר. יש לגבות ולתכנן שמירת מידע אישי לפני שימוש אמיתי. אין סיסמת מנהל ברירת מחדל; בלי משתנה token, ניהול חסום.

להדגמת רכישה בלבד, לאחר החלטה מפורשת לגבי תנאי ההדגמה:

```bash
export ACADEMY_PAYMENT_MODE=simulation
export ACADEMY_BOOKING_TERMS_APPROVED=1
node scripts/academy-server.mjs
```

יש לעצור את התהליך הקודם לפני הפעלה מחדש. הסימולציה דורשת `NODE_ENV=development`; מפתח חתימה קבוע שנשמר מחוץ ל־git מאפשר בקשות חוזרות עמידות גם לאחר restart. הדגל אינו אישור לחיוב אמיתי ואינו מחליף אישור משפטי לתנאי הרכישה בייצור. אין לפרסם את טיוטות המועדים האמיתיות רק לשם בדיקת זרימה; בדיקות אוטומטיות יוצרות בסיסי נתונים זמניים ומאשרות מועדים בתוכם בלבד.

משתנים נוספים:

| משתנה | תפקיד |
|---|---|
| `ACADEMY_DB_PATH` | נתיב SQLite מתמשך חלופי; אינו מתאים לדיסק זמני בפונקציה serverless |
| `ACADEMY_HOST` | כתובת האזנה; ברירת מחדל loopback |
| `ACADEMY_PORT` | פורט; ברירת מחדל 5174 |
| `ACADEMY_ALLOWED_ORIGINS` | רשימת origin מדויקים, מופרדים בפסיק; HTTPS בלבד מחוץ ל־loopback |
| `ACADEMY_ADMIN_TOKEN` | token ניהול חזק, לפחות 32 תווים; אף פעם לא `VITE_*` |
| `ACADEMY_SIMULATION_SECRET` | מפתח חתימה מקומי חזק, לפחות 32 תווים; אף פעם לא `VITE_*` |

האזנה מחוץ ל־loopback דורשת token חזק ורשימת origins מפורשת וכן reverse proxy שמספק TLS. HTTP ישיר של שרת Node אינו פתרון TLS. אין CORS עם wildcard ואין אימות באמצעות cookie. שינויי מנהל דורשים Bearer; origin זר נדחה. מגבלות בקשות מקומיות: 120 שינויי מצב לדקה לכל כתובת חיבור, ו־20 ניסיונות אימות מנהל שנכשלו לדקה. אלו מגבלות פיתוח בזיכרון, אינן חומת אש או מנגנון מניעת שימוש לרעה מבוזר לייצור.

## חוזה API מקומי

כל שגיאה מחזירה `{error:{code,message}}`, ללא סודות או פרטי כרטיס. הנתונים הדינמיים אינם נשמרים ב־cache.

| נתיב | בקשה ותוצאה |
|---|---|
| `GET /api/academy/catalog` | `{dates,commerce:{mode,ready,bookingTermsApproved},pricing}`; מועדים מאושרים/מפורסמים/עתידיים בלבד |
| `POST /api/academy/quote` | `{dateId,couponCode?,email?}` → סכום לפני הנחה, הנחה וסכום סופי באגורות; אימייל חובה לקופון שמוגבל ללקוח |
| `POST /api/academy/orders` | `Idempotency-Key` ומידע `{dateId,customer:{name,email,phone},termsAccepted:true,couponCode?,marketingConsent?,installments?:1}` → `orderId`, `orderAccessToken`, סטטוס, סכום, תוקף מושב ו־`simulation:true` |
| `GET /api/academy/orders/:id` | Bearer של ההזמנה; סכום וסטטוס מאומת, לקוח, מועד, אסמכתא והכנה |
| `POST /api/academy/simulation/pay` | Bearer של ההזמנה; `{orderId,outcome?:'succeeded'|'failed'}`. אירוע חתום נוצר ונבדק בשרת; אינו מחייב כסף |
| `POST /api/academy/simulation/webhook` | JSON מדומה חתום; `X-Academy-Timestamp` במילישניות UTC ו־`X-Academy-Signature`; אינו webhook של Grow |
| `GET /api/academy/admin/summary` | Bearer מנהל; מועדים, קופונים, הרשמות, הכנסות, outbox ויומן פעולות |
| `GET /api/academy/admin/dates`, `/coupons`, `/registrations`, `/orders`, `/revenue`, `/outbox` | רשימות ודוחות ניהול בלבד |
| `POST /api/academy/admin/dates` | מועד חדש בטיוטה, ללא פרסום או אישור |
| `PATCH /api/academy/admin/dates/:id` | עדכון סמינר/תאריך/מקום/קיבולת/סטטוס/פרסום. שינוי מהותי מחייב אישור חדש; עם הרשמות פעילות הוא נחסם |
| `POST /api/academy/admin/dates/:id/approve` | `{checksConfirmed:true,publish?:true,openRegistration?:true}`; מאשר שבוצעו בדיקות מקום, חגים והתחייבויות קודמות |
| `POST /api/academy/admin/dates/:id/reject` | `{reason?}`; דחייה ללא הרשמות פעילות |
| `POST /api/academy/admin/coupons` | קוד פרטי, סוג, ערך, תוקף, הגבלות ומכסה; אינו מופעל בלי `active:true` |
| `PATCH /api/academy/admin/coupons/:id` | שינוי/השבתת קופון |
| `POST /api/academy/admin/orders/:id/refund` | החזר סימולציה idempotent בלבד |
| `POST /api/academy/admin/outbox/:id/retry` | פתיחת ניסיון חדש למשימה; **אינו שולח הודעה** |

סטטוסי הזמנה: `pending`, `paid`, `failed`, `expired`, `refund_required`, `refunded`. אין מקור אמת בדפדפן. כישלון תשלום משחרר מושב. retry לאחר כישלון/פקיעת תוקף דורש מפתח הזמנה חדש, כדי לא לעקוף idempotency של אותה הזמנה.

## הודעות ו־CRM

תבניות שירות עבריות ב־`server/message-templates.mjs` כוללות אישור הדגמה, הכנה, תזכורת, המשך וביטול. הן אינן טוענות שנשלח דוא״ל או שנוצרה קבלה. דרישות הכלים המדויקות טעונות אישור הדרכה. הסכמת שיווק נשמרת בנפרד ואינה תנאי להרשמה.

`drainOutbox(deliver)` דורש adapter מפורש ואינו מופעל על ידי שרת ההדגמה. קיימים idempotency key קבוע לכל הודעה, ניסיון חוזר עם backoff, עד שמונה כישלונות, ותפוגת lease של worker לאחר חמש דקות. ספק השליחה חייב לתמוך באותו idempotency key כדי למנוע כפילויות אם worker קורס אחרי שליחה ולפני שמירת תוצאה. זהו דפוס at-least-once, לא הבטחת exactly-once אצל ספק חיצוני. מנהל רואה סטטוס ויכול לפתוח ניסיון חוזר; פרטי שגיאת ספק לא נשמרים כדי למנוע הדלפת מידע אישי.

לא בוצעו כתיבות ל־Fireberry, Resend, Morning או Grow. אין worker מופעל, ולכן כל המשימות נשארות pending עד חיבור ספק מאושר. מיפוי קורסים/מחזורים/רשומות קיימות, אימות יעד ההודעות, קישורי חומרי ההכנה וקבלות הם חסמי השקה.

## Morning / Grow — מה אומת ומה עדיין חסום

נערכה קריאה בלבד בתיעוד הציבורי הרשמי. אין חשבון או credentials זמינים, אין בקשות checkout לספק ואין שימוש בכרטיסים או ארנקים.

המקורות שנבדקו:

1. [Grow Regular Payment Overview](https://developers.grow.business/reference/regular-payment-overview): יצירת דף תשלום מאובטח בשרת, מזהי `userId`/`pageCode` שהספק מוסר, וקישור עם תוקף של עשר דקות. פרטי לקוח וסכום חייבים לצאת מהשרת.
2. [Grow Create Payment Process](https://developers.grow.business/reference/create-payment-process): התיעוד מציג `paymentNum` בין 1–12 ו־`maxPaymentNum`. שישה תשלומים אפשריים בחוזה ה־API, אך הזכאות וההגדרה בחשבון הסוחר לא אומתו. האתר המקומי מקבל כרגע תשלום אחד בלבד.
3. [Grow Server to Server Callback](https://developers.grow.business/reference/server-to-server-callback): `notifyUrl` ב־HTTPS, callback עם שדות form ולא JSON, ו־acknowledgement באמצעות `ApproveTransaction`. התשלום עשוי להתבצע גם אם acknowledgement נכשל. **לא אומת חוזה חתימה/אימות מקור מספק בעמודים שנקראו**; אין לקבל callback בלתי מאומת כאישור הרשמה.
4. [Grow Approve Transaction](https://developers.grow.business/reference/approve-transaction-5): method ושדות רשמיים מתועדים; לא מומש או נוסה נגד הספק ללא אישור וחשבון.
5. [Grow Live Environment](https://developers.grow.business/reference/live-environment): הספק דורש בדיקת logs/callbacks/HTTP200/acknowledgement לפני הפעלת פרטי ייצור.
6. [Grow Testing Environment](https://developers.grow.business/reference/testing-environment): אזהרה מפורשת שארנקים Bit/Google Pay/Apple Pay עלולים לחייב כסף אמיתי גם בתהליך בדיקות. בבדיקת sandbox עתידית מאושרת יש להשתמש רק בכרטיסי הבדיקה שהספק מפרסם.
7. [Morning Developers](https://developers.morning.co/): המבוא מתאר JSON/HTTPS, OAuth2 ו־token של שעה. מפרט endpoints הנחוץ לא נגיש במלואו בקריאה שנערכה; אין להסיק endpoints ישנים או מערכת מסמכים מחיבור Grow בלבד.

`MorningGrowAdapter` ב־`server/payment-adapters.mjs` מגדיר גבול עבור `createCheckout`, `verifyWebhook`, `refund`, `reconcile`; כל פעולה נכשלת במפורש עם `PAYMENT_UNAVAILABLE`. לא הומצאו endpoints, חתימות או מפתחות ספק. `api/academy.ts` מחזיר 503 בסביבה serverless; הוא אינו מנסה להפעיל SQLite זמני ב־Vercel. התאמת נתיבי catch-all לשרת פיתוח מתבצעת ב־Vite; הגדרת ניתוב ייצור אינה מחברת סליקה.

## תנאי השקה שלא הושלמו

- אישור מועדים: המקום, חדר/כתובת מדויקים, חגים והתחייבויות ללקוחות קיימים. מקור לוח השנה אינו אישור להרשמה.
- תנאי הרשמה, ביטול/דחייה, החזרים, מינימום משתתפים ופרטיות מאושרים; דגל פיתוח אינו תחליף לכך.
- בסיס נתונים מתמשך לייצור עם גיבויים, שחזור, מניעת overselling בטרנזקציות, הצפנה/גישה ושמירת מידע אישי. SQLite מקומי אינו מתאים לפונקציות Vercel עם דיסק זמני או לכמה מופעים נפרדים ללא אחסון משותף.
- אימות מנהל לייצור: זהויות אישיות, הרשאות, MFA/rotation/revocation, יומן מנהל לפי זהות. token סביבתי אחד הוא כלי פיתוח בלבד.
- פרטי סוחר Morning/Grow מורשים, מפרט רשמי נגיש, adapter ליצירת hosted checkout ו־lookup מאומת, חוזה callback/acknowledgement, בדיקות sandbox, refund/reconciliation ואישור ספק לייצור. תשתית hosted checkout נבדקה עם ספק מדומה בלבד; אין להעתיק את חתימת הסימולציה לתוך חוזה הספק.
- אימות רו״ח למעמד עוסק פטור ופרטי מסמכי תשלום; חיבור הפקת קבלה אמיתית וקישור אליה.
- אימות תשלומים עד שש מול חשבון הסוחר; טקסטים וסכומים לפי התנאים האמיתיים.
- adapters מאושרים לשליחת שירות/CRM ו־worker עם ניטור וניסיון חוזר; ספק עם idempotency.
- הסרת כל יכולת סימולציה מייצור; TLS, origin/abuse controls, secrets management, monitoring, בדיקת זרימה מלאה וקבלת אישור מפורש לפרסום.
